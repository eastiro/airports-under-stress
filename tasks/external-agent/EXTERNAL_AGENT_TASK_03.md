# External Agent Task 03 — 把飞机轮转卡片重构成能讲清楚的延误故事

> 执行入口：`EXTERNAL_AGENT_TASK_02_03_MASTER.md`。本文件是轮转故事详细规格，不要脱离 Master 单独启动。

## 背景

用户实际阅读“飞机轮转故事”后无法快速理解每个故事的区别，并指出航班号、起飞/到达、延误分钟和周转分钟极小。

Codex 已在 1366×768 桌面视口和源码中复核：

- 航班号与计划时间：`8px`；
- “起飞 / 到达”标签：`8px`；
- 延误数字：`11px`；
- 航段状态：`8px`；
- 周转标签：`7px`；
- 五张航段卡片被压进单行，每张最小宽度只有 `150px`；
- `延误级联 / 延误恢复 / 紧周转 / 传播与恢复` 对非航空访客区分度不足；
- 当前状态被放在航段卡片上，但“传播/恢复”实际描述的是前一段晚到与下一段起飞之间的关系；
- 当前 `turn` 来自下一条链路的 `ScheduledTurnMinutes`，页面却笼统写成“XX分钟周转”，没有展示 `ActualTurnMinutes`，语义不完整。

这是数据叙事与信息层级任务，不是单纯放大字体。

## 任务 A：先修正周转与传播语义

### 1. 区分两种时间

不得继续只显示含糊的“51分钟周转”。每个相邻航段连接器至少区分：

- `计划时刻间隔`：当前 `ScheduledTurnMinutes`；
- `实际地面周转`：当前 `ActualTurnMinutes`。

并在方法说明中明确：

- 这些航段由实际观察到的同一机尾号连接；
- “计划时刻间隔”是该机尾最终执行的两班航班在公开计划中的时间差；
- 它不单独证明这是航空公司事先冻结的同一架飞机轮转计划，因为实际机尾可能发生调配或替换。

### 2. 把传播状态放到连接器

每两个航段之间新增清楚的地面连接器，例如：

```text
SFO 地面衔接
计划时刻间隔 51 分钟 · 实际地面 57 分钟
晚点 +31 → +53 分钟（增加 22 分钟）
延误继续传到下一班
```

连接器根据已有数据计算：

- 上一段 `ArrDelay`；
- 下一段 `DepDelay`；
- `delayDelta = next DepDelay - previous ArrDelay`；
- 传播：两者均超过15分钟；
- 恢复：上一段到达延误超过15分钟，下一段起飞回到15分钟以内；
- 如果仍延误但分钟减少，要写“追回 X 分钟，但仍晚点”，不要只写“传播”。

不要把描述性关系写成因果结论。

### 3. 重新审计“紧周转”故事

当前 story-3：

- 类型：`tight-turn`；
- 机尾号：`N210WN`；
- LAS 的计划时刻间隔为 `0` 分钟；
- 对应实际地面周转为 `45` 分钟；
- 上一段到达延误 `+59` 分钟，下一段起飞延误 `+104` 分钟。

这不能直接讲成“航空公司给同一架飞机安排0分钟周转”。请重新检查故事选择规则：

- 优先使用 `ActualTurnMinutes` 识别真实紧周转；
- 候选实际周转建议在 `15–40` 分钟之间，并至少存在一次传播关系；
- 计划时刻间隔必须大于0；
- 如果没有语义干净、访客容易理解的紧周转样本，删除这一故事类型并替换为“延误被放大”或另一条有明确数据证据的故事；
- 修改故事选择后要保持4条故事、真实机尾连续性和现有P0物理检查，不得手工捏造案例。

## 任务 B：补齐航班时间字段

当前卡片只有一个模糊的 `scheduled` 起飞时刻。修改 `scripts/build_v0_data.py` 和生成数据，使每个航段在可取得时包含：

- 计划起飞 UTC；
- 实际起飞 UTC；
- 计划到达 UTC；
- 实际到达 UTC；
- 起飞延误分钟；
- 到达延误分钟。

要求：

- 使用现有 `p0_flights.parquet` 和 `p0_chain_links.parquet` 中的真实字段或可复核时间运算；
- 第一个航段也必须尽量通过机尾号、日期、航司、航班号、起讫机场等稳定字段回查完整记录；
- 时间跨午夜时显示日期变化，例如 `01:00Z · 次日`，不能只留一个无法判断日期的时刻；
- 数据缺失时显示明确的“未报告”，不要显示含义不明的破折号。

## 任务 C：重写四个故事名称

主导航必须使用普通访客能立刻理解的结果句，不再把专业分类词当主要标题。

建议方向，以重新生成后的实际数据为准：

| 技术类型 | 中文主标签方向 | 英文主标签方向 |
|---|---|---|
| cascade | 连续4班仍在晚点 | Delay continued across 4 flights |
| recovery | 晚到后被下一班追回 | The next flight recovered |
| tight-turn | 实际周转只剩 X 分钟 | Only X minutes on the ground |
| mixed | 先传递，后来追回 | Delay spread, then recovered |

要求：

- `延误级联 / 紧周转 / 传播` 等术语可作为次级技术标签或方法说明保留，但不能继续成为第一次阅读时唯一可见的名字；
- 每个标签必须根据故事的真实 `propagated / recovered / actual turn` 数据生成，不能把数字写死；
- 每个故事顶部增加一句不超过两行的普通话结论，直接回答“这架飞机后来发生了什么”。

## 任务 D：重做故事时间线布局

### 桌面端

- 不再使用 `280px 左栏 + 5张150px小卡` 的拥挤结构。
- 推荐结构：
  1. 顶部全宽故事摘要；
  2. 下方连续航段时间线；
  3. 航段之间插入独立的“地面衔接”连接器；
  4. 点击某一航段或连接器时，在固定说明区解释这一时刻发生了什么。
- 可以横向滚动，但在 1366×768 下应至少完整展示3个航段和2个连接器，并明显提示可继续浏览。
- 也可设计为可逐步播放的故事轨道，但必须提供播放/暂停与直接点选，不能强制访客等待动画。

### 字号下限

以下为桌面端最小值，不允许用7–9px承载关键信息：

- 航班号：`15–17px`；
- 起讫机场代码：`28–34px`；
- 计划/实际时间：`13–15px`；
- “计划起飞 / 实际起飞 / 计划到达 / 实际到达”标签：至少 `11–12px`；
- 延误数字：`17–22px`；
- 传播/恢复结果：至少 `12px`；
- 地面衔接时间：至少 `12–14px`；
- 普通说明正文：至少 `14px`；
- 非关键元数据也不得低于 `10px`。

### 视觉层级

每张航段卡第一眼顺序应为：

1. 航班号；
2. `SAN → SFO` 路线；
3. 计划与实际起飞/到达；
4. 起飞、到达延误；
5. 航段状态。

连接器第一眼顺序应为：

1. 衔接机场；
2. 实际地面周转；
3. 晚点分钟如何变化；
4. “继续传递 / 追回但仍晚 / 已恢复”的普通话结论。

### 手机端

- 改为纵向时间线，不把5张卡横向压缩到手机宽度。
- 航段与衔接连接器交替出现，保持相同语义顺序。
- 不依赖仅悬停可见的信息。

## 任务 E：增加故事引导

- 选择故事后，在时间线上方提供一句“阅读方法”，例如：`先看每班到达晚点，再看下一班起飞时还剩多少晚点。`
- 用一个简短图例解释：红色=仍超过15分钟，薄荷绿=回到15分钟以内，琥珀=晚点减少但尚未恢复。

- 保留“传播是描述性连续关系，不单独证明因果”的边界，但字号必须可读。
